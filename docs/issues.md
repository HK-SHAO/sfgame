# 用户体验问题清单

老大（即用户）会定期把问题新增在此文档中。

针对每一个问题，研发人员（或 AI Agent 等）在阅读后需要着手核实、尝试复现、深度研究和思考。

注意老大的问题或建议不一定完全属实、合适或是最佳决策，要以第一性原理、产品体验和工程可靠且优雅为要义，批判性的研究、执行和回复。

每一个问题的状态要及时更新，例如是否已阅读，是否在执行中，执行结果或简要报告要体现。报告一定要挑重点，省略低信息量（即业界高频出现的模式）的细节，不能省略 bug 的修复或缺陷的改进。

老大负责最终给每个问题结束工单（用【ok】表示，只有老大才能结束工单，研发人员/Agent 没有权限），在此前研发绝不能忽视。

此文件仅供老大更改。如需汇报状态编辑 docs/issues 目录，文件名为 #N.md，参考业界的 issue 相关经验进行编辑。

- #10 了解 docs 中关于设计、玩法、创意。要有浪漫感，例如信息论、熵、庞加莱回归、宇宙演化相关的“文学”浪漫感。已有文档仅作为参考，可以跳出其中，也可以做好取舍。目前已经实现的 2 个关卡可以视作简单教学关卡，再设计三个教学关卡（完成度要十分的高，并充分验证），为之后的更多需要人工设计的关卡打好基础。例如，设计好一些基本元素、原子能力，其他研发可以像搭积木一样微调或组合出全新的关卡。因此每个关卡是可以完美 json（或yaml） 序列化的，这样也方便玩家 DIY 关卡进行传播。在设计一套足够强大的“乘法式”或“涌现式”原子能力后，也需要一个 skill 能够真实的指导新手用基于序列化的某种“协议”搭建关卡。需要特别注意不要堆砌元素或玩法，而是提高少量真正足够精选的原子能力。已有的关卡也完美移植到这一套系统。其中一个特点是，可序列化的关卡与状态能够在一个“无头”的引擎内部运行模拟，这也方便调试或接入算法或ai。对于关卡设计的要义、行业优秀的经验等，强烈建议搜索足够多高质量资料学习。最后强调，此需求的开发不设限，但克制化意味着不要让项目大规模膨胀和对各种想象做好取舍。技术部分参考 docs/development.md
