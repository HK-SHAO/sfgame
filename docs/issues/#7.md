# #7 性能与流畅度大幅提升（渲染 GPU 化 + iOS 专项 + JS 微优化）

- **状态**：已实现、自测通过（`bun run check` 81 项全绿）；iOS 实机体验待老大验收
- **日期**：2026-08-04（第一轮渲染 GPU 化；第二轮倍速诊断与 JS 微优化；wasm 方案评估后已移除；第三轮 iOS Safari 渲染专项）

## iOS Safari 渲染专项（第三轮）：根因与修复

### 根因（外部证据 + 实机数据）

- **iOS Safari 的 WebGL 全部经 ANGLE→Metal 后端**（iOS 15.4 起默认），WebKit 官方确认该后端同内容 GPU 负载显著更高、内容"本质是 GPU 受限"（bug 255987），并有帧呈现依赖（bug 254912，可致有效帧率减半到 30fps）与 IOSurface 分配（bug 255860）等配套问题；Chrome/Android（Vulkan/GL）、macOS Safari（后端已修复）无此问题——与"只有 iOS Safari 卡"的现象完全吻合。
- 我们的场景放大了后端开销：全屏画布 dpr2（~1.7MP）+ **MSAA 4×** ≈ 6.7M 采样/帧；**全程 alpha 混合**（连不透明天空/地形都走混合）；每帧 4~7 万顶点 + ~1.5MB 上传走 Metal buffer 翻译。SwiftShader 实测动态层 3.2 万顶点/0.74MB。
- 帧节奏隐患：渲染门控 `>=16.67ms` 在 60Hz 下浮点临界，iOS rAF 抖动（16.2~16.6ms）会跳过半数渲染 → 16/33ms 交替呈现，视觉似 30fps。

### 修复（全部已落地，SwiftShader 实机验证）

1. **帧节奏**：渲染门控加 1ms 容差（60Hz 每帧必渲、120Hz 仍隔帧）——消除 16/33ms 交替。
2. **`antialias: false`**：砍 MSAA 4×（iOS Metal 后端最大开销之一）；几何化矢量边缘由分辨率保证。
3. **不透明/混合两趟**：静态背景（天空/地形/光晕/目标静态）烘焙到离屏纹理（resize 时重建），每帧以不透明 quad 一次 blit（关混合）——动态层保持 alpha 混合。顶点 ~7 万→3.2 万、上传 ~1.5MB→0.74MB。**翻案**：第一轮"GPU 负载可忽略故不缓存背景"的决策基于"iOS GPU 足够快"假设，已被实机推翻。
4. **blend 每帧幂等重设**：canvas 尺寸变更会重置上下文状态（resize 后混合失效的隐患）。
5. **`?perf=1` 调试叠加层**（独立模块 `src/ui/perf.ts`，与游戏逻辑解耦）：实时帧间隔 p50/p95/max、tick/batch 耗时、顶点数/上传字节、loop 帧数；点击一键复制 JSON 回报。iPhone 实测判据：持续 ~33ms = GPU/合成受限，16/33 交替 = 帧节奏，偶发尖峰 = 抖动型。
6. **loop 帧循环 try/catch**：渲染异常不再静默冻结（rAF 链断裂不可见），显式上报。
7. 顺带修复：渲染门控 + perf 面板空数组崩溃（首窗第一帧无间隔）。

### 后续（若实机仍 <60fps，按序）

- 顶点双缓冲（A/B 轮换 + STREAM_DRAW）规避 bufferSubData→Metal 同步 stall
- 轨迹线 instancing（ANGLE_instanced_arrays）上传再降 ~6×
- 粗指针设备 trailLen 24→16、头点分段 10→8（并入降级阶梯）

## 第二轮回顾：wasm 求解器——已评估并移除（实测无收益）

## 第一轮诊断：瓶颈在渲染栅格化，不在物理

- iOS Safari 的 Canvas 2D 为 **CPU 栅格化**（WebKit）。旧渲染每帧 ~400 粒子 × 24 轨迹点 ≈ **9600 段描边**，即使分桶也要 20+ 次 Path2D stroke + 渐变对象/精灵烘焙，CPU 成本随 段数×dpr 非线性增长——正是 iOS 明显差于桌面/Android 的原因。
- 流体求解器（~7.5k 格 × ~39 趟/步）在桌面 <2ms，非瓶颈；粒子/刚体步进同为次要项。

## 第一轮取舍：WebGL1

- **WebGL 1.0**：iOS 8+ / 全部 Android WebView 可用且 GPU（Metal）加速——兼容性最优解，正中"iOS 最差"的病灶。
- **WebGPU：不做**。iOS 支持太新、WebView 覆盖不足。

## 第二轮：wasm 求解器——已评估并移除（实测无收益）

### 过程

- 针对"iOS 物理数值计算性能差"的假设，用 MoonBit 实现逐位一致的 wasm 求解器（12.4KB、零依赖、`bun run check` 全绿含逐位一致性测试），并配弱引擎自动选择（启动探测）。
- **真机实测推翻假设**（iPhone iOS 18.7 / macOS Safari / Chrome 三平台）：

| 平台 | fluid.step JS | fluid.step wasm |
|---|---|---|
| iPhone 18.7 Safari | 0.520ms | 0.767ms（+48%）|
| macOS Safari 26.5 | 0.510ms | 0.708ms（+39%）|
| Chrome 150 | 0.643ms | 1.558ms（+142%）|

- **wasm 在所有实测平台都更慢**：JIT 引擎的 JS typed-array 数值循环已接近原生速度，wasm 的调用/转换开销反成负资产；"无 JIT 的 WKWebView"场景未在任何实测中出现。按第一性原理（实测优先、少即是多），**已移除全部 wasm 代码**（native/、fluid-wasm、FluidLike 抽象、wasm 测试、bench wasm 对比、build:native 脚本），保留有价值的 JS 微优化。
- 教训：**上"加速技术"前必须先跑真机基准**（详见 pitfalls I7 改写）。

## 第三轮（前一轮）：倍速（16×）卡顿诊断与修复——物理无关，是帧预算余量问题

### 实机数据（new-bch.md，微优化后）

| 组件 | iPhone | macOS Safari | Chrome |
|---|---|---|---|
| fluid.step | 0.520ms | 0.510ms | 0.643ms |
| LevelSim.step | 0.485ms | 0.503ms | 0.642ms |
| batch 构建 | 0.263ms | 0.208ms | 0.335ms |
| **倍速帧 16×** | **8.942ms** | **9.333ms** | **11.745ms** |

**iOS Safari 物理不是瓶颈**（比桌面还快，仅占帧预算 3%）。倍速帧三平台全部 <16.7ms——修复后 16× 有 30~46% 余量。

### 倍速卡根因（修复前）

- **帧成本 × 倍率线性放大**：16× 时每帧 16 个 tick ≈ 8~12ms，顶到预算边缘，任何抖动（GC/热降频/合成）立即掉帧；CDP 6× 节流实测 16× 单帧 76ms（弱设备上每帧掉 5 帧）。
- **追帧爆帧**：旧 `MAX_TICKS_PER_FRAME=60`，掉一帧后单帧最多 60 tick ≈ 30ms——卡顿被放大器放大。
- **iOS 热降频**：倍速 = 持续 50%+ CPU，iPhone 主动降频。

### 修复

- `loop.ts`：追帧上限 60→**24**——最坏单帧 ≈12ms+渲染，欠账顺延下帧消化（短暂慢放而非爆帧）；稳态（16×=16 tick）与暂停回归均不触顶。`tests/loop.test.ts` 同步更新。
- `fluid.ts` **逐位微优化**（确定性测试守护）：固体索引表（enforceBoundary 免全阵扫描）、buoyancy 去分支（固体 t=0 不变量）、GS 预乘 divH2（f64 精度，与逐次计算逐位相同）、3×3 展开、行基提升、`|0` 替代 floor。JS 求解器 -17%（0.609→0.508ms bun），**所有平台所有倍率受益**。
- bench 新增「**倍速帧**」测量项（rate×tick+批构建 = 倍速下每 60Hz 帧的真实 CPU 成本），`bench.html?rate=16` 可直接在 iPhone 上量；`bun scripts/bench-browser.ts 1,6 3`（CDP + CPU 节流）一键可复现。

## 物理一致性保证（各平台/速率/分辨率/尺寸）

- **平台**：物理层为纯 IEEE 浮点 JS（无随机、无平台相关 API），同输入必逐位同输出——新增确定性回归测试（流体场与整局两次运行逐位一致）。
- **速率**：固定步长 `SIM_DT=1/60`，倍速只改每真实秒的 tick 数、不改 dt——轨迹逐位不变（loop.test 断言 dt 恒等）。
- **分辨率/尺寸**：网格由关卡世界尺寸推导（76×56/cell 0.75），与屏幕像素无关；渲染按 contain 适配，物理不随屏幕变化。
- **降级阶梯**：只降示踪粒子数/DPR（视觉层），不触碰物理。

## 第一轮改动（渲染 GPU 化，未变）

**架构（公共 API 零变化，控制器/UI 无感）**

- `src/core/batch.ts`（新）：纯计算顶点批构建器——线段加宽、椭圆扇、径向渐变盘、虚线圆等全部展开为彩色三角形。无 DOM，可无头测试（tests 分层不变量保持：只 import core/game/sim）。
- `src/ui/gl.ts`（新）：WebGL1 薄层——单程序（位置+逐顶点色）、单动态 VBO、每帧一次 `drawArrays`；含上下文丢失/恢复处理（iOS 内存压力回收）。
- `src/ui/render.ts`（重写）：场景绘制全部输出到顶点批。删除 bg 离屏缓存、Path2D 分桶、渐变精灵 Map 等 Canvas 时代补丁。

**随重构获得的改进（非纯搬运）**

- **逐顶点颜色取代分桶近似**：旧实现受 strokeStyle 状态机所迫，透明度/温度离散分桶（4×5 档）；现在每段带精确 RGBA，一次提交——视觉更细腻且代码更简。
- **修复隐藏 bug**：旧 `drawPlane` 在高空（影子淡出高度以上）**连飞机本体一起 return，飞机凭空消失**；重写后影子淡出与本体绘制分离（详见 pitfalls D8）。
- 线宽几何化（GL lineWidth 多平台恒 1）；径向渐变用扇形逐顶点插值，免每帧 createRadialGradient。

**物理与调参（数值位级不变）**

- 热路径 `Math.hypot` → 内联 sqrt、投影迭代数提升为局部量——`tests/solutions.test.ts` 的通关时刻守护（±2s 实测全中）证明数值未漂移。
- 渲染 GPU 化后重调降级档位：移动端初始粒子档 128→240、轨迹点 12→24（旧限制来自 CPU 描边，现已移除），dpr 上限放宽至 2；自适应降级阶梯机制（EMA+慢帧计数）原样保留。
